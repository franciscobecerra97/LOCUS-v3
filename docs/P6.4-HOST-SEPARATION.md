# P6.4 Host-Separation Gate

Status: `Same-host configurable staging complete; actual host separation blocked on infrastructure`

Audit date: 2026-08-03

D023 planning clarification: 2026-08-04

## Current demonstrated boundary

P6.3 starts distinct mutually authenticated party processes with distinct
certificates, configurations, and SQLite databases. That is same-host process
separation only. It is below every P6.4 tier and is not described as host or
administrative independence.

The available workstation was inspected without changing it:

- Docker Desktop is installed and its Linux engine is available through one
  `desktop-linux` context;
- WSL contains one Ubuntu distribution and Docker Desktop's distribution;
- Docker reports its normal seccomp isolation, but all project containers
  remain under one Docker Desktop engine/VM;
- Multipass, Vagrant, Hyper-V PowerShell, QEMU, VirtualBox, and VMware command-
  line runtimes are not installed or available.

Creating more Docker containers or WSL distributions would not satisfy the
project's “separate local VMs” tier because they would still share the same
underlying host/engine boundary. No P6.4 execution result is therefore claimed.

## Configurable same-host staging

The new `LOCUS-party-endpoint-setup-v1` boundary keeps public endpoint
configuration outside the frozen Compose file:

- `deploy/party-endpoints.json` is the runnable same-host setup. It maps
  parties 1--5 to Docker service names `party1`--`party5`, all on port 8443.
- `deploy/party-endpoints.five-host.example.json` is a safe synthetic example
  showing where five later DNS names or IP addresses are entered.
- `deploy/compose.party-endpoints.yaml` is an additive overlay. It mounts the
  selected setup read-only into the networkless provisioner.
- Provisioning uses the same checked values for certificate SANs, client
  endpoints, peer endpoints, and each service listener. It rejects unknown
  fields, malformed/duplicate JSON, reordered or missing parties, unsafe host
  values, duplicate separate-host addresses, and a changed setup applied to an
  existing deployment.

Run all five containers on the current host with:

```console
uv run --frozen python tasks.py deployment-configurable-smoke
```

The command validates the fully merged Compose model, builds the pinned LOCUS
image, starts all five party containers plus the scoped local supporting roles,
runs correct/restart/one-party-unavailable recoveries, scans output, and removes
the disposable containers and volumes. It remains a same-host result.

The command completed successfully on 2026-08-03. All five party services
became healthy; correct recovery, recovery after restart, and recovery with one
party unavailable passed; the output-safety scan passed; and the disposable
containers, networks, and volumes were removed. The image packaging gate now
also requires both native suite crates so future local builds cannot silently
omit the aPPSS core. This execution is development validation, not retained
P6.4 evidence.

## Relationship to the D023 integrated reference system

D023 inserts P7.5 before P8 so the loopback UI/client gateway, admission,
discovery, storage, resolver, and all five party services run as one connected
same-host reference system. That work reuses service contracts and deployment
controls, but it receives a new deployment profile rather than changing the
meaning of frozen `LOCUS-compose-deployment-v2` or this P6.4 staging setup.

Completing P7.5 on one Docker engine will establish end-to-end system
integration only. It will not demonstrate separate VMs, separate network hosts,
or independent administration, and therefore will not close P6.4. Conversely,
the current configurable deployment smoke and current in-memory P7 UI remain
component controls; running them separately is not a substitute for the P7.5
UI-to-containers flow.

P8/P9 must evaluate the integrated system at the exact separation tier used by
the run. Until external infrastructure is available, that tier is same-host
only. A later multi-host execution must still satisfy every validation item in
this document and retain a separately versioned result; topology labels alone
cannot promote the same-host result.

For future provisioning, copy the five-host example to a new local path, replace
only the five `host` values (and ports if required), and set
`LOCUS_PARTY_ENDPOINT_SETUP` to that path. Do not label or retain a multi-host
result until the five services have actually been placed on those hosts and the
validation run below passes. The endpoint file prepares configuration and
certificates; it does not itself distribute containers or establish firewall,
storage, or administrative separation.

## Infrastructure needed to resume

Provide either:

1. five disposable local VMs, each with a distinct virtual NIC and durable
   disk; or
2. five disposable network hosts under one administrator.

All machines must contain synthetic research state only. Tier 3 additionally
requires actual independent operators; separate accounts or labels controlled
by one person do not qualify.

## Exact validation run

For each Yi/aPPSS and 2-of-3/3-of-5 P6.3 profile, the resumed gate must record
privacy-safe public observations for:

- unique host, endpoint, certificate, and service identities;
- one disjoint durable party-state root per host;
- absence of shared mounts containing OPRF keys, TPASS state, recovery inputs,
  recovery secrets, wrapping keys, protected-key plaintext, or credentials;
- firewall rules allowing only the declared coordinator/party protocol edges;
- descriptor/bootstrap discovery of the exact authenticated endpoints;
- topology captured before startup and again after all services are ready;
- correct recovery through an exact valid holder subset;
- failure with fewer than the recovery threshold;
- authorization failure with fewer than four authorizers;
- restart of one holder from only its own durable state, followed by catch-up
  and exact retry behavior; and
- cleanup of every disposable VM/host credential, certificate, database, log,
  and synthetic protected key.

The result must state exactly one demonstrated tier. It must not infer
independent administration from networking, certificates, different disks, or
different VMs.
